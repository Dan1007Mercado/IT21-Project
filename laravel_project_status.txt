INTSEC LARAVEL PROJECT STATUS REPORT
===================================

Project name: INTSEC
Purpose: Integrated Intrusion Monitoring and Incident Response System
Stack: Laravel 12, Blade, Tailwind CSS, MySQL, Chart.js
Current implementation style: custom Blade + Laravel middleware routes, not Filament-based admin panels

1. CURRENT SYSTEM STATUS
------------------------

The project is a working security-monitoring and incident response foundation. Core capabilities include authenticated access, role-based authorization, authentication logging, IP enrichment, audit logging, system settings, and a custom admin interface.

2. IMPLEMENTED USER ROLES
-------------------------

A. Guest / unauthenticated user
- Can access the login page.
- Can submit credentials for authentication.
- Is blocked from protected routes until authenticated.

B. Standard User
- Can authenticate and access the authenticated application session.
- Can view the main dashboard and basic monitoring views.
- Can review their own authentication activity.
- Can update their own account profile and password.
- Cannot access administrator-only routes or settings screens.

C. Administrator
- Can access the protected administration area.
- Can review security monitoring information.
- Can modify supported security settings.
- Can review audit logs.
- Can operate in the admin monitoring flows supported by the application.

16. AUTOMATIC INCIDENT CREATION & ALERTING (NEW)
-----------------------------------------------

Implemented (2026-09-12):
- A threshold-driven monitoring flow was added that creates SecurityEvents, SecurityAlerts, and Incidents automatically when IP request frequency exceeds the configured system setting `repeated_ip_activity_threshold`.
- The threshold is read dynamically from system settings using `IntsecSettings::getInt('repeated_ip_activity_threshold')` — no hardcoded values.
- The comparison uses strict greater-than (`>`): only counts strictly larger than the configured threshold will trigger spike recording and incident creation.

Deduplication strategy:
- To avoid flooding, the monitoring logic looks up recent incidents for the same `source_ip` within a 60-minute activity window and with a non-final status (not `resolved` or `false_positive`).
- If such a recent incident exists, it is updated (event_count, last_detected_at) instead of creating a new incident.
- Only when there is no suitable recent incident will a new SecurityEvent + SecurityAlert + Incident be created within a DB transaction.

Where implemented:
- Detection hook integrated into the attack-frequency monitoring flow in `app/Http/Controllers/DashboardController.php` (method `attackFrequency()` now calls `processIpActivity()` for ips over threshold).
- Deduplication and creation logic implemented in `processIpActivity()` within the same controller for now (keeps logic local and testable). It creates SecurityEvent -> SecurityAlert -> Incident transactionally and records an AuditLog entry.

22. RECOMMENDED NEXT STEPS
-------------------------

- Move the automatic detection logic into a scheduled command or queued job to avoid running detection on every page render (recommended for production scale).
- Add a system setting to control the deduplication window length (e.g., `ip_activity_dedup_minutes`) so administrators can tune the 60-minute window used today.
- Consider adding a small Laravel Event when an automatic incident is created so real-time broadcasting (Echo/WebSockets) can be attached later.
- Add a Filament resource for Blocked IPs and Security Alerts if an admin wants a richer CRUD experience.
